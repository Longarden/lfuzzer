step1 · 섹션헤더(SHT) 폴백 트러스트 바운더리 재분석

ELF 퍼저 연구 · 2026-07-14 교수님 미팅용 · glibc 2.39 디버그 ld.so + gdb 재현 실험 · worker-step1

결론 — SHT 폴백은 존재하지 않는다 (미재현 / 방어됨).
DYNAMIC의 버전 주소 태그(DT_VERSYM/DT_VERNEED)의 d_ptr을 0으로 지우면, 런타임 링커는 섹션헤더(.gnu.version Addr=0x50e)의 값을 대신 읽지 않는다. 로더는 오직 DYNAMIC의 d_ptr만 신뢰한다. 0을 넣으면 그대로 0(=로드 베이스, ELF 헤더 영역)을 읽어 세그폴트(VERSYM) 또는 "unsupported version 17791"(VERNEED) 오류를 낸다. → SHT는 버전심볼의 독립 공격표면이 아니다. 7/03 회의의 0x50e 관측은 폴백이 아니라, 링커가 DYNAMIC와 SHT에 같은 값을 일관되게 써서 생긴 우연의 일치다(readelf는 SHT본을, 로더는 DYNAMIC본을 읽음).

1. 목적과 가설

가설(7/03 교수님 회의): ELF DYNAMIC에서 버전심볼 주소 태그(d_ptr)를 0으로 지워도, 런타임에는 섹션헤더(SHT)의 값(관측 사례 0x50e류)이 대신 읽히는 폴백 경로가 있는 것으로 보인다. SHT는 런타임에 원래 쓰이지 않는(무결성 기대 없는) 영역이므로, 폴백이 사실이면 DYNAMIC을 건드리지 않고 SHT만으로 버전심볼을 조작하는 별도 공격표면이 된다.

검증 목표: 디버그 ld.so를 gdb로 실행해, 실제로 읽히는 버전 주소가 (a) DYNAMIC 값인지 (b) SHT 값인지 소스라인 근거와 함께 확정한다. 버그를 지어내지 않는다.

3. 변종 제작 — DYNAMIC의 d_ptr만 0으로

스크립트 scripts/craft_versym_zero.py는 PT_DYNAMIC을 파싱해 대상 태그의 d_tag는 유지하고 d_un(값)만 0으로 덮는다. SHT(.gnu.version Addr=0x50e, .gnu.version_r Addr=0x520)는 손대지 않는다.

변종0으로 지운 DYNAMIC 태그파일 오프셋원래 값 → 새 값
versym_zeroDT_VERSYM (0x6ffffff0)0x2f480x50e → 0x0
verneed_zeroDT_VERNEED (0x6ffffffe)
DT_VERNEEDNUM (0x6fffffff)		0x2f28
0x2f38		0x520 → 0x0
0x1 → 0x0

readelf 대조 — "DYNAMIC은 0인데 SHT는 그대로 0x50e"

# versym_zero.elf
$ readelf -d prac_versym_zero.elf | grep -i VERSYM
 0x000000006ffffff0 (VERSYM)             0x0        <-- DYNAMIC: 지워짐

$ readelf -S prac_versym_zero.elf | grep -i gnu.version
 [ 8] .gnu.version    VERSYM   000000000000050e  0000050e   <-- SHT: 그대로
 [ 9] .gnu.version_r  VERNEED  0000000000000520  00000520

$ readelf -V prac_versym_zero.elf     # readelf는 SHT를 읽으므로 여전히 정상 파싱
 .gnu.version  Addr: 0x50e  ... 0(*local*) 2(GLIBC_2.34) 1(*global*) 3(GLIBC_2.2.5)

즉 정적 도구(readelf)는 SHT본을 읽어 멀쩡해 보이지만, 런타임 로더가 무엇을 읽는지는 아래 gdb가 판정한다.

4. 런타임 실행 결과

바이너리결과해석
prac.elf (원본)Hello, ELF World! (exit 0)정상
versym_zeroSegmentation fault (exit 139)버전 포인터가 NULL → 역참조 크래시
verneed_zerounsupported version 17791 of Verneed record (exit 127)base+0의 ELF 매직을 vn_version으로 읽음

핵심 신호: 17791 = 0x457F. 이는 ELF 매직 바이트 7f 45("\x7fE")를 16비트 리틀엔디언으로 읽은 값이다 (python3 -c 'struct.unpack("<H", b"\x7f\x45")' → 17791). 로더가 로드 베이스(=ELF 헤더)에서 Verneed를 읽었다는 직접 증거이며, SHT가 가리키는 0x520의 진짜 레코드(vn_version=1)를 읽었다면 원본처럼 정상 동작했을 것이다.

5. gdb 소스라인 근거 (A) — VERNEED

브레이크포인트 dl-version.c:184 (if (ent->vn_version != 1)). 문제의 ent은 바로 위 180번 줄에서 계산된다:

판정: d_ptr=0 → ent = base+0 → vn_version = 0x457f(ELF 매직). 반면 SHT가 가리키는 base+0x520에는 진짜 레코드(vn_version=1)가 멀쩡히 있는데도 로더는 그것을 읽지 않았다. 폴백 없음.

6. gdb 소스라인 근거 (B) — VERSYM

브레이크포인트 dl-version.c:294 (map->l_versyms = D_PTR(map, l_info[VERSYMIDX(DT_VERSYM)])). D_PTR은 DYNAMIC 엔트리의 d_ptr로만 주소를 만든다(ldsodefs.h:88).

===== BREAK dl-version.c:294 (compute l_versyms) =====
map->l_addr (base)  = 0x7ffff7fbe000
map->l_versyms (computed from zeroed DYNAMIC d_ptr) = (nil)
  base + 0x50e (what SHT .gnu.version says) = 0x7ffff7fbe50e  <- would be here IF SHT fallback existed
l_versyms is base+0x50e (SHT)? 0   (0 => SHT value IGNORED)
l_versyms is NULL? 1   (version ptr NULL because DYNAMIC d_ptr was 0)

--- bytes at SHT base+0x50e (the real .gnu.version array, ignored by loader) ---
0x7ffff7fbe50e: 0x0000 0x0002 0x0001 0x0003 0x0001 0x0001 0x0003 0x0000

판정: l_versyms = NULL(≠ base+0x50e). SHT의 진짜 .gnu.version 배열 (0 2 1 3 1 1 3 — readelf -V와 동일)이 base+0x50e에 그대로 있음에도 로더는 그 주소를 쓰지 않는다. 이후 재배치 단계 do-rel.h:126-133에서 version[symndx]가 NULL을 역참조 → SIGSEGV. 이것이 exit 139의 원인이다.

7. 왜 폴백이 구조적으로 불가능한가 — 소스 트러스트 바운더리

로더가 버전 주소를 얻는 유일한 경로 PT_DYNAMIC (l->l_ld) | get-dynamic-info.h:45 for (dyn = l->l_ld; dyn->d_tag != DT_NULL; dyn++) | get-dynamic-info.h:69 info[i] = dyn; <- l_info[]는 DYNAMIC 엔트리 포인터만 저장 v map->l_info[VERSYMIDX(DT_VERSYM/VERNEED)] | dl-version.c:180 ent = map->l_addr + dyn->d_un.d_ptr | dl-version.c:294 l_versyms = D_PTR(map, l_info[VERSYM]) (= base + d_ptr) | do-rel.h:126 version = D_PTR(map, l_info[VERSYM]) v 실제로 읽는 주소 = map->l_addr + (DYNAMIC의 d_ptr) <- 섹션헤더는 등장하지 않음

런타임 로더 소스 전체에서 섹션헤더를 읽는 코드를 검색한 결과:

$ grep -rln "e_shoff|ElfW(Shdr)|sh_offset|sh_addr|e_shnum" \
       dl-*.c rtld.c get-dynamic-info.h dynamic-link.h do-rel.h dl-version.c
(결과 없음)

# 참고: glibc elf/ 전체에서 섹션헤더를 읽는 유일한 파일은 sprof.c
#       -> "Read and display shared object profiling data" (오프라인 프로파일러, 런타임 경로 아님)

즉 런타임 링커는 설계상 섹션헤더 테이블을 파싱하지 않는다. 버전 주소는 DYNAMIC의 d_ptr이라는 단일 신뢰원(single source of trust)에서만 온다. 따라서 "DYNAMIC을 지우면 SHT로 폴백"은 존재할 수 없다.

8. 7/03 관측(0x50e)의 재해석

  • 왜 0x50e가 양쪽에 있었나: 링커가 .gnu.version 섹션을 0x50e에 배치하고, 동시에 DT_VERSYM에도 같은 주소를 써 넣는다. 둘은 항상 일치하도록 생성된다.
  • 관측의 정체: readelf는 SHT본(0x50e)을 보여주고, 로더는 DYNAMIC본(0x50e)을 읽는다. 값이 같아 "SHT가 읽힌다"처럼 보였을 뿐, 실제 판독원은 DYNAMIC이다.
  • 결정적 반증: 두 값을 강제로 어긋나게 만들면(DYNAMIC=0, SHT=0x50e 유지) 로더는 0을 따라가 크래시/오류를 낸다. SHT의 0x50e를 절대 쓰지 않는다.

9. 연구 함의 · 한계 · 다음 단계

함의 (퍼징 표면): SHT 단독 뮤테이션 = 버전심볼 공격표면 아님 런타임 버전 해석에 영향을 주려면 반드시 DYNAMIC(또는 그 d_ptr이 가리키는 데이터)을 건드려야 한다. SHT만 바꾸는 뮤테이션은 로더 버전 처리에 도달하지 못한다 → 해당 방향의 시드/변이 예산은 낮춰야 한다.

대신 유효한 표면(관찰됨): DYNAMIC의 d_ptr을 0이 아닌 임의 오프셋으로 밀면, 로더가 그 주소를 그대로 신뢰해 vn_version/versym을 임의 메모리에서 읽는다. 이는 SHT 폴백보다 더 강한, 실재하는 조작 경로다(step2 후보).

한계: (1) prac.elf 단일 케이스·glibc 2.39 한정. 다른 버전/뮤슬(musl) 로더는 별도 확인 필요. (2) 메인 실행파일의 버전 처리 경로만 확인. 공유 라이브러리 의존성 체인에서의 동작은 동일 소스라인이나 별도 재현은 안 함. (3) d_ptr을 0이 아닌 유효 오프셋으로 조준하는 익스플로잇 가능성은 이번 범위 밖(다음 단계).

다음 단계: ① DYNAMIC d_ptr을 통제된 오프셋으로 조준해 "임의 주소 버전 판독" PoC(step2). ② musl / 구버전 glibc 교차검증. ③ 이 소스라인 근거를 퍼저 mutator_dynamic_v3.py의 필드 우선순위(SHT 강등, DYNAMIC d_ptr 승격)에 반영.
