step3 — LD(BFD) vs Gold 링커 Differential

다이나믹 섹션 조작 ELF의 링커별 처리 divergence를 이용한 evasion 공격표면 · 2026-07-13 · 미팅 0714

한 줄 결론. 계측용 Gold 링커 빌드를 복구(별도 빌드 트리 + all-gold 타겟 + MAKEINFO=true 우회)해서 실행 바이너리를 얻었고, 동일한 조작 DSO 하나에 대해 세 주체의 판정이 갈리는 재현 가능한 divergence를 포착했다: 런타임 ld.so: 정상 실행 Gold: 링크 수용 LD(BFD): "file in wrong format" 거부

즉 실행도 되고 Gold로 링크도 되지만, LD 기반 분석 도구만 "깨진 파일"로 오판하는 ELF를 만들 수 있다 — 정확히 교수님이 말씀하신 링커별 동작 차이 = evasion 표면.

1. 목적과 evasion 프레이밍

ELF의 동적 링킹 정보는 두 곳에 중복 표현된다: 섹션 헤더 테이블(.dynamic, .dynsym, .dynstr 섹션)과 프로그램 헤더의 PT_DYNAMIC 세그먼트. 이 이중 표현을 도구마다 다르게 신뢰한다는 점이 공격 표면이다.

  • 런타임 로더(ld.so)는 섹션 헤더를 완전히 무시하고 프로그램 헤더 / PT_DYNAMIC만 사용한다.
  • LD(BFD)는 DSO를 심볼 소스로 받아들일 때 섹션 헤더 테이블의 정합성을 먼저 검증한다(포맷 인식 단계).
  • Gold는 필요한 섹션(.dynsym 등)을 타입으로 타겟 조회하고 나머지 섹션 헤더 이상은 관대하게 넘긴다 — 로더에 더 가깝다.

세 주체의 신뢰 경계가 어긋나는 지점에 조작을 심으면, 한 도구는 통과시키고 다른 도구는 거부하는 "링커 의존적 ELF"가 만들어진다. 분석 파이프라인이 LD 기반이면 실물은 멀쩡히 도는 바이너리를 놓친다.

2. Gold 링커 빌드 복구 성공

알려진 문제(메모리): --enable-gold 한 줄로는 안 되고, 상위 트리 빌드가 doc/*.stamp / makeinfo 단계에서 깨진다.

복구 전략 — 서브디렉토리 타겟 격리 + doc 우회

전체 트리(make all)를 짓지 않고, Gold와 그 의존물만 짓는다. 별도 빌드 트리를 만들어 상위 configure로 서브빌드를 생성한 뒤 all-gold 타겟만 호출하고, texinfo 문서 생성은 MAKEINFO=true(=no-op)로 무력화했다.

mkdir ~/binutils-build-gold && cd ~/binutils-build-gold
~/binutils-src/binutils-2.42-afl/configure \
    --enable-gold --enable-ld=no --disable-gdb --disable-sim \
    --disable-gprofng --disable-werror MAKEINFO=true CC=gcc CXX=g++
make -j8 MAKEINFO=true all-gold        # 전체 트리 아닌 gold 타겟만
configure
exit 0 — doc/aoutx.stamp 경로 자체를 all-gold가 안 건드림
make all-gold
exit 0 — 소요 2분 27초 (22:13:13 → 22:15:40)
산출 바이너리
~/binutils-build-gold/gold/ld-new (100 MB)
버전 확인
GNU gold (GNU Binutils 2.42) 1.16

삽질 노트: 최초 시도에서 nohup make &를 WSL 일회성 세션에 띄웠더니 세션 종료와 함께 프로세스가 죽어(로그에 헤더 1줄만 남음) 진행이 안 됐다. 백그라운드 작업을 세션 밖 관리 프로세스로 옮기자 정상 완료. 빌드 자체는 한 번에 뚫렸고, doc/makeinfo 벽은 all-gold 타겟 격리로 애초에 마주치지 않았다.

3. 실험 설계

요소내용
대조 링커 ALD(BFD) · ~/binutils-build-afl-bfd-clean/ld/ld-new · GNU ld 2.42
대조 링커 BGold · ~/binutils-build-gold/gold/ld-new · GNU gold 1.16
입력물main.o(foo 호출) + libfoo.so.1(foo 제공) — 조작 대상은 후자의 다이나믹 정보
링크 명령LINKER -shared --no-undefined -o out main.o <조작 libfoo>
왜 -shared/--no-undefinedgold이 ET_EXEC/ET_DYN을 직접 입력으로 거부하는 문제 회피 + --no-undefined로 foo 심볼 해결을 강제해 DSO의 다이나믹 심볼 파싱을 load-bearing으로 만듦
판정exit code + stderr 분류(OK/ERROR/HANG/CRASH), 출력 아티팩트의 DT_NEEDED 비교

주의(메모리 반영): gold은 .o를 링크하는 도구라 실행 가능한 ET_DYN/ET_EXEC를 직접 주면 거부한다 → 본 설계는 ".o + 조작된 입력 DSO" 링크 시나리오로 구성했다.

4. 결과

4-1. Baseline — 둘 다 정상

손상 없는 libfoo.so.1에 대해 LD·Gold 모두 exit 0. 다이나믹 섹션 18 엔트리 정상.

4-2. DYNAMIC 세그먼트 필드 조작 12종 — divergence 없음(중요한 발견)

Elf64_Dyn 배열의 DT_STRTAB / DT_STRSZ / DT_SYMTAB / DT_SYMENT / DT_GNU_HASH / DT_SONAME 등을 필드 단위로 손상시킨 12개 뮤턴트 — LD·Gold 모두 12/12 OK, divergence 0.

왜 안 갈렸나 (핵심 인사이트). 섹션 헤더가 온전하면 두 링커 모두 .dynsym/.dynstr 섹션에서 심볼을 읽고, PT_DYNAMIC 세그먼트의 DT_*는 링크 시점에 사실상 무시한다. DT_STRTAB를 파일 밖으로 보내도, DT_SONAME 오프셋을 범위 밖으로 밀어도 링크가 성공한 이유다. → 링크 타임 divergence를 노리려면 세그먼트(DT_*)가 아니라 섹션 헤더 테이블을 흔들어야 한다는 방향 전환의 근거.

4-3. 방향 전환 → 섹션 헤더 조작에서 divergence 포착

■ PRIMARY divergence (B2) — 수용/거부가 완전히 갈림

조작. .dynamic 섹션 헤더의 sh_type 필드를 SHT_DYNAMIC(6) → 0x99(무효)로 1바이트 변경.

파일 오프셋 0x38f4:  06 00 00 00   →   99 00 00 00
(libfoo.so.1, .dynamic = 섹션 index 16, 섹션헤더 파일오프셋 0x38f0)
주체결과근거(관측)
런타임 ld.so정상 실행./runtest → foo(1)=43, exit 0 (섹션헤더 무시)
GoldACCEPTrc=0, out_b2_gold.so 생성, DT_NEEDED=[b2_dyn_shtype.so], foo 해결됨
LD (BFD)REJECTrc=1 · "error adding symbols: file in wrong format"

⇒ 동일 파일 하나가 실행되고 Gold로 링크되지만 LD는 "포맷 자체가 틀렸다"며 거부. 재현 100%.

SECONDARY divergence (B1) — 실패 양상이 갈림

조작. ELF 헤더의 e_shstrndx(섹션명 문자열 테이블 인덱스)를 0xffff(범위 밖)로 변경.

링커동작stderr
LD (BFD)관대 — 경고 후 진행warning: corrupt string table index … 이후 심볼명 못 읽어 undefined reference to `foo'
Gold엄격 — 즉시 중단error: section name section has wrong type: 0 / bad section name offset

둘 다 최종 rc=1이지만 LD는 graceful degrade(경고), Gold는 hard error. 손상 위치에 따라 엄격/관대 역할이 뒤바뀐다(B2에선 Gold가 관대, B1에선 LD가 관대)는 점이 흥미롭다 — 두 파서의 검증 순서가 근본적으로 다르다는 신호.

5. 근본 원인

LD(BFD) 경로
DSO를 심볼 소스로 열 때 포맷 인식(bfd_check_format) 단계에서 섹션 헤더 테이블 전체 정합성을 검증. .dynamic의 sh_type이 어긋나면 bfd_error_wrong_format(bfd.c:743 "file in wrong format")으로 조기 거부.
Gold 경로
gold/dynobj.cc에서 필요한 섹션을 타입으로 골라 타겟 읽기(SHT_DYNSYM에서 export 심볼 확보). .dynamic 섹션의 잘못된 sh_type은 결정 경로에 없어 통과 → 로더처럼 동작.
런타임 ld.so
섹션 헤더를 아예 읽지 않음. 프로그램 헤더 + PT_DYNAMIC만 사용 → 섹션 헤더 손상에 완전 면역.

세 파서가 "무엇을 진실로 보는가"가 다르다: LD=섹션헤더 정합성 우선, Gold=필요한 섹션 타겟 조회, ld.so=세그먼트 전용. 이 신뢰 경계 불일치가 divergence의 원천이다.

6. 결론 · evasion 함의

  • 빌드 리스크 해소. Gold 계측 빌드는 all-gold 타겟 격리 + MAKEINFO=true로 2분대에 복구됨. 이후 실험에 재사용 가능한 링커 쌍 확보.
  • 재현 가능한 divergence 확보. .dynamic sh_type 1바이트 변조로 실행 OK · Gold 링크 OK · LD 거부. 이는 "링커/도구 의존적 ELF"의 존재 증명.
  • 공격 관점. 분석·재링크 파이프라인이 BFD(ld, objcopy 등 동일 백엔드)를 쓰면 이 파일을 "wrong format"으로 버리는데, 바이너리는 정상 구동 → 탐지 우회 / 분석 회피 표면.
  • 퍼저 관점. 우리 세그먼트-헤더 뮤테이터가 노려야 할 고수익 필드는 (링크타임 divergence 기준) PT_DYNAMIC의 DT_*가 아니라 섹션 헤더의 sh_type / e_shstrndx 등 "이중 표현이 갈리는 필드". 12/12 무반응 vs 섹션헤더 즉시 반응이 그 지도를 그려준다.

7. 다음 단계

  • divergence를 자동 오라클로 승격: 뮤턴트 → {ld.so 실행, gold 링크, ld 링크} 3자 판정을 differential 오라클로 삼아 "실행⋀gold수용⋀ld거부" 삼중조건 히트만 수집.
  • 섹션 헤더 필드 전수 스윕(sh_type/sh_link/sh_info/sh_entsize/sh_offset × 각 섹션)으로 divergence 유발 필드 맵 완성.
  • BFD 쪽 조기거부 지점을 소스 레벨로 정확히 특정(_bfd_elf_object_p 계열)해서, "왜 여기서만 wrong_format인가"를 링커 버그/과엄격 판정으로 리포트할지 판단.
  • lld(LLVM), mold 추가 대조군 편입 → 3-way를 N-way로 확장, 링커 생태계 전반의 divergence 스펙트럼 확보.
