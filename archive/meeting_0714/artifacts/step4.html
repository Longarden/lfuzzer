Step4 — 분석기 Differential: DT_EXTRATAGIDX Evasion 사례

분석기 간 Dynamic Section 해석 불일치 — DT_EXTRATAGIDX 절단 사례

Step4 · Analyzer Differential (Evasion 프레이밍) · 2026-07-13 작성

한 줄 요약. readelf(시스템/소스빌드 모두), objdump, pyelftools는 패치된 태그 0xDEADBEEFFFFFFFFD를 전부 <unknown>으로 표시해 "의미 없는 필드"로 취급한다. 그러나 실제 동적 링커(ld.so)는 이 태그의 하위 32비트만 보고 이를 정상적인 DT_DEBUG 슬롯(내부 인덱스 60)으로 인식·저장하며 프로그램은 정상 실행된다. 즉 "분석기가 보는 것"과 "로더가 실행하는 것"이 서로 다르다 — 정적 분석 기반 도구가 놓치는 필드를 런타임은 유효하게 처리하는, 전형적인 analysis-vs-runtime 괴리(evasion 소재)다.

1. 배경 및 Evasion 프레이밍

동적 링커/로더 연구팀(Lfuzzer)의 세그먼트 헤더 뮤테이션 퍼징에서, DYNAMIC 세그먼트의 태그(d_tag)를 조작한 PoC가 하나 발견되었다. 이 사례가 흥미로운 이유는 단순 크래시가 아니라 "보안 분석기가 인식하지 못하는 필드를 로더는 정상적으로 실행에 사용한다"는 구조적 문제이기 때문이다.

디스어셈블러/분석기는 저마다(그리고 버전마다) ELF 다이나믹 태그를 해석하는 테이블·로직이 다르다. 분석기가 "알 수 없는 태그"로 건너뛰는 필드를 실제 로더가 유효한 필드로 처리한다면, 그 필드는 분석 리포트에는 나타나지 않지만 런타임 동작에는 영향을 미치는 은닉 채널이 된다. 이는 정적 분석 우회(evasion)의 한 형태로 볼 수 있다.

2. PoC 구성

PoC는 정상 실행되는 prac.elf(PIE, 동적 링킹)의 DYNAMIC 세그먼트에서 DT_DEBUG(태그 값 21) 엔트리 하나를 골라, 태그 필드만 아래 값으로 덮어써 만들었다 (craft_extratag_poc.py, 본 worktree에 사본 포함):

필드원본패치 후
d_tag0x0000000000000015 (DT_DEBUG = 21)0xDEADBEEFFFFFFFFD
d_val0 (로더가 실행 중 채움)변경 없음 (0)

패치된 태그를 상위 32비트(0xDEADBEEF, 임의의 "쓰레기" 마커)와 하위 32비트(0xFFFFFFFD)로 나눠 보면, 하위 32비트가 핵심이다. 0xFFFFFFFD는 부호 있는 32비트로 해석하면 -3이며, glibc의 DT_EXTRATAGIDX 매크로는 이 값을 "확장 태그 슬롯 2번"으로 환산한다 (아래 3절 참조). 즉 상위 32비트는 완전히 버려지고, 하위 32비트만으로 "이건 알려진 확장 태그다"라고 판단하는 것이 이 사례의 근본 원인이다.

3. 근거: glibc get-dynamic-info.h 소스

동적 링커가 .dynamic 배열을 순회하며 각 태그를 내부 인덱스 테이블 l_info[]에 매핑하는 코드는 다음과 같다 (glibc-2.39/elf/get-dynamic-info.h, 실측 소스 라인):

핵심은 DT_EXTRATAGIDX 매크로 정의이다 (/usr/include/elf.h:989):

#define DT_EXTRATAGIDX(tag)  ((Elf32_Word)-((Elf32_Sword) (tag) <<1>>1)-1)
#define DT_EXTRANUM  3

(Elf32_Sword)(tag)에서 64비트 d_tag를 32비트로 truncate한다. 우리 패치값의 하위 32비트 0xFFFFFFFD는 -3이 되고, <<1>>1은 부호비트를 정리하는 관용구로 값 자체는 그대로 -3 유지 → DT_EXTRATAGIDX = -(-3)-1 = 2. 2 < DT_EXTRANUM(3)이므로 56행 분기가 채택된다.

5. 결론

ELF 파일
d_tag = 0xDEADBEEFFFFFFFFD
→
정적 분석기
readelf/objdump/pyelftools
"<unknown>" → 무시
동일 ELF 파일
→
ld.so 런타임
하위 32비트만 검사
DT_DEBUG 슬롯(i=60)으로 처리
  • 무엇을 놓치는가 — readelf(2개 빌드 모두)·objdump·pyelftools는 64비트 d_tag 전체를 알려진 태그 상수와 정확히 일치시키는(exact-match) 방식으로만 인식한다. glibc 로더처럼 "하위 32비트만 잘라서 재해석"하는 로직이 없어, 상위 32비트에 아무 값이나 넣으면 태그 전체가 <unknown>으로 빠진다.
  • 왜 로더는 다른가 — DT_EXTRATAGIDX 등 glibc의 태그 분류 매크로들은 애초에 32비트 ELF와 64비트 ELF를 같은 매크로로 처리하기 위해 Elf32_Sword로 캐스팅한다. 이 하위호환 캐스팅이 64비트 ELF에서는 "상위 32비트 검증 누락"이라는 부작용을 낳는다.
  • evasion 관점 요약 — 공격자가 이 필드를 페이로드 은닉이나 분석 회피에 쓸 수 있는가는 DT_DEBUG류 슬롯 자체의 활용도에 달려 있어 별도 검증이 필요하지만, "정적 분석기가 통째로 놓치는 필드를 런타임이 유효하게 소비한다"는 구조적 gap 자체는 재현 완료. 정적 분석 리포트만 보고 "이 바이너리에 특이 태그 없음"이라 결론 내리면 틀린 판단이 된다.

6. 한계 및 다음 단계

  • Ghidra 미검증 — headless 분석기(analyzeHeadless)가 이 WSL 환경에 설치돼 있지 않아 실측하지 못했다. 다음 미팅 전 설치해 동일 PoC로 재현 여부 확인 필요.
  • readelf 버전 간 실차이 미발견 — 이번엔 같은 2.42 소스 2개 빌드였다. 실제 "버전" 차이를 보려면 오래된 binutils(예: 2.30대, DT_EXTRATAGIDX 관련 로직이 다르거나 DT_EXTRANUM 값이 다른 시절)를 별도로 빌드해 비교해야 한다.
  • 다른 태그로 확장 미실시 — RUNPATH/RPATH 중복 태그, 중복 DT_NEEDED 등 "분석기가 첫 번째만 보여주고 로더는 다르게 처리"할 수 있는 다른 후보들은 시간 관계상 이번 라운드에서 다루지 못했다. 다음 스텝 후보로 남긴다.
  • evasion 실증까지는 미완 — "분석기가 놓친 필드에 실제로 악성 목적의 정보를 숨겨서 로더가 그걸 이용해 동작을 바꾸는" 완전한 PoC(예: 이 슬롯 값을 이용해 실행 흐름을 바꾸는 것)까지는 안 갔다. 현재는 "표시 vs 저장" 괴리의 재현에 그친다.
