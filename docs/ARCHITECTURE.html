Lfuzzer — ELF64 / 동적 링커 차등 퍼저

입력 ELF의 3개 영역(섹션 헤더 · .dynamic · 프로그램 헤더)만 겨냥해 뮤테이션하고, gold vs BFD 링커와 ld.so 로더가 갈라지는 지점을 관찰하는 파이썬 퍼저 + 차등 연구 툴킷.

구조 계보(lineage): Melkor ELF Fuzzer (Alejandro Hernandez, Black Hat 2014). Melkor의 모듈 역할(melkor.c → fuzz_<metadata>.c → generators.c + logger.c)과 메타데이터 의존성 레벨 개념을 구조적으로 미러링한다. 언어 포팅이 아니라 역할 매핑 — Lfuzzer는 파이썬이다.

1 · 왜 이 퍼저인가

일반 ELF 퍼저는 파서(readelf/objdump)를 깨뜨리는 데 그친다. Lfuzzer는 한 단계 더 들어가서 정적 링커가 만든 산출물을 런타임 로더 ld.so가 어떻게 소화하는가를 본다. 타깃은 세 겹으로 쌓인다:

타깃: 툴체인 3층

  • 정적 링커 — ld(BFD), ld.gold
  • 런타임 로더 — glibc ld-linux-x86-64.so.2
  • 분석기 — readelf / objdump / Ghidra

스코프: 오직 3개 영역

  • SHDR 섹션 헤더 테이블 — 분석기가 신뢰하는 뷰
  • .dynamic DT_ 태그 — 로더가 실제 읽는 뷰
  • PHDR 프로그램 헤더 — 세그먼트/로드 지도
차등 각(differential angle) — Melkor에 없는 것. Melkor는 orc(뮤턴)를 만들어 하나의 타깃에 던진다. Lfuzzer는 같은 뮤턴을 gold와 BFD 양쪽에 링크하고, 그 결과를 같은 ld.so로 실행해서 "링커 A는 통과, 링커 B는 거부/크래시", "분석기는 정상, 로더는 세그폴트" 같은 구현 간 불일치를 버그 후보로 채굴한다. 단일 타깃 크래시가 아니라 divergence가 신호다.

2 · 배워야 할 단 하나의 개념 — ELF 메타데이터 의존성 레벨

Melkor 슬라이드 p.45–46의 핵심. ELF 메타데이터는 상위가 하위를 가리키는 의존성 트리다. 상위 레벨을 깨면 하위 전체가 무효가 되어 링커가 즉시 포기하고, 결국 커버리지가 얕아진다. 그래서 규칙: 깊은 레벨일수록 나중에, 혹은 아예 건드리지 않는다 (fuzz-deep-last) — 의존성을 살려 링커/로더가 코드를 더 깊이 실행하게 만든다.

PHT 영역 SHT 영역 .dynamic 영역 ↓ 아래로 갈수록 의존성 깊음 → 뮤테이션 우선순위 낮춤

실전 함의: mutator_field_v2(PHT)와 mutate_elf_v4(SHDR)는 상위 레벨이라 자주 때리고, mutator_dynamic_v3(.dynamic)는 DT_STRTAB/DT_SYMTAB 같은 critical 태그일수록 확률(likelihood)을 낮춰 의존성을 보존해야 한다 — 이것이 목표 상태다.

현재 구조의 위치 — 정직하게. Lfuzzer는 아직 통합 의존성-레벨 엔진이 없다. mutate_elf_v4의 repair_pht()가 keep 모드에서 PHT 교차필드 불변식을 국소적으로 복구하고, mutator_dynamic_v3가 DT 태그 그래프를 의식하는 부분적 처리는 있으나 — 영역 간 레벨 순서(HDR→PHT/SHT→dynamic)와 깊이별 확률 스케줄링을 조율하는 상위 정책은 부재하다. 위에서 새로 넣은 generators/·logger/가 likelihood 뼈대를 깔았고, 이를 각 mutator가 채택해 fuzz-deep-last를 실행하는 것이 로드맵 R1의 실체다.

4 · 전체 파이프라인 — 통합형 (collect-once → dual oracle)

핵심 개선: 오늘은 크래시 사냥(A)과 차등 관찰(B)이 실행을 각자 따로 한다. 통합형은 뮤턴트 하나를 한 번만 실행해 관측벡터를 수집하고, 그 결과를 두 오라클이 나눠 먹는다 — 작업1(크래시)과 작업2(divergence)가 같은 실행 위에서 병렬로 돈다. 비싼 Ghidra만 티어2(생존자에만). 설계 상세: docs/UNIFIED_PIPELINE.md.

SHDR .dynamic PHDR gold 링크 bfd 링크 작업1 크래시 작업2 divergence 티어2
현재 → 통합 한 줄. 현재는 A(autorun_v3)와 B(exp_*)가 실행을 각자 한다(ld.so 두 번, 분석기는 B에서만). 통합형은 실행을 한 번 수집해 크래시 오라클과 divergence 오라클이 공유 — 실행비용 절반, 두 신호 동시. 앞 섹션의 "분석기 뷰가 중간에 떠 보이던" 혼란은 이 그림에서 작업2 divergence로 자리를 잡았다.

5 · 퍼징 규칙 & 제너레이터

Melkor의 규칙 실행 모델을 파이썬으로 미러링한다. 모듈마다 규칙 함수의 배열을 갖고, 각 규칙은 likelihood 게이트(rand() < -l)를 통과할 때만 발화한다. critical 필드를 만지는 규칙은 그 안에서 확률을 스스로 낮추어 의존성을 보존한다(fuzz-deep-last의 실행판).

Melkor 개념Lfuzzer 구현
규칙 배열 + __attribute__((constructor)) 등록모듈 상단 RULES = [rule_fn, ...] 리스트, import 시 채워짐
-l likelihood (기본 10% / aggressive 70%)if random.random() < likelihood: 게이트, CLI 인자로 조절
critical 필드는 규칙 내부에서 확률↓DT_STRTAB/DT_SYMTAB 등에서 로컬 확률 하향
generators.c + numbers.hgenerators/generators.py + numbers.py — 경계값·반가치 데이터
logger.clogger/logger.py — 발화 규칙·오프셋 로깅 (재현 근거)

규칙 한 개가 어떻게 생겼는가 (개념 스케치, 실제 시그니처는 각 mutator 파일 참조):

# mutators/mutator_dynamic_v3.py  (개념)
from generators import generators as G

def rule_corrupt_dt_needed(buf, dyn, likelihood):
    # 의존성 얕음(문자열 인덱스만) → 기본 확률로 발화
    if random.random() < likelihood:
        ent = pick(dyn, tag="DT_NEEDED")
        ent.d_val = G.oob_stroffset(buf)      # numbers.py 경계값
        log.fire("DT_NEEDED.d_val", ent.offset)   # logger 기록
    return buf

def rule_corrupt_dt_strtab(buf, dyn, likelihood):
    # CRITICAL: STRTAB 포인터 → 확률 자체를 낮추어 의존성 보존
    if random.random() < likelihood * 0.25:
        ...

RULES = [rule_corrupt_dt_needed, rule_corrupt_dt_strtab, ...]

6 · 차등층 (differential/)

Lfuzzer만의 층. 두 축의 불일치를 실험 파일로 고정한다:

축 A · gold ≠ BFD

같은 뮤턴을 두 링커로 링크 → 같은 ld.so로 실행. 링크타임 수용/거부 차이, 그리고 통과했더라도 런타임 로더 거동 차이를 관찰.

exp_goldbfd_diff/exp_d01..d24.py (strip_sht, dynstr_nonul, verneed_edge, shnum_zero, runpath…), exp_r1/r5/r6(decoy dynamic, phdr vs sht, unknown enum), 집계 exp_display_all.py.

축 B · 로더 ≠ 분석기

readelf/objdump/Ghidra가 보는 뷰와 ld.so가 실제 로드하는 뷰의 차이. "분석기 정상 · 로더 세그폴트" 또는 그 반대가 신호.

Ghidra 헤드리스 ghidra_scripts/DumpDynamic.java, exp_r7_ghidra_dtag / exp_r8_ghidra_symcount, parser_diff/.

실행 예: cd differential/exp_goldbfd_diff && python exp_d05_verneed_edge.py → gold/BFD 각각 링크·실행 결과를 표로 출력. 모든 실험 일괄은 python exp_display_all.py. 경로는 common.py → lfuzzer/config.py로 승격한다.

9 · 이해도 자가진단 — 깊은 이해 vs 암기 변별 10문항

아래 10개는 정의를 외운 사람과 메커니즘을 이해한 사람을 가르도록 설계됐다. 암기자는 명사를 나열하고, 이해한 사람은 왜 그런가 · 안 그러면 무슨 일이 나는가 · 무엇과 무엇의 트레이드오프인가를 말한다. 각 문항의 펼치기에 "무엇을 가르나 + 깊은 답의 핵심"을 넣어, 스스로 답한 뒤 대조할 수 있게 했다.

왜 SHDR·.dynamic·PHDR 셋만 건드리나? 넷째로 심볼 테이블을 직접 뮤테이트하면 오히려 커버리지가 떨어질 수 있는 이유는?
가르는 것: 의존성 레벨
암기 답: "3영역만 하기로 정해서." 깊은 답: 심볼/스트링은 하위 레벨이라, 상위(PHT·.dynamic)가 깨지면 링커/로더가 그 지점 전에 포기 → 하위까지 도달 못 함. 얕은 고레버리지 층에 집중하는 게 fuzz-deep-last의 실천.
gold와 BFD가 같은 뮤턴을 서로 다르게 링크한다는 게 왜 '버그 후보'인가? 둘 다 크래시 안 나도 신호가 되는 이유는?
가르는 것: differential oracle
암기 답: "둘이 다르니까." 깊은 답: 정답(ground truth)이 없는 파서에서 두 독립 구현의 불일치 = 최소 한쪽이 스펙 해석을 틀렸다는 증거. 크래시는 divergence의 부분집합일 뿐, 조용한 동작 차이도 스펙 모호성/버그를 가리킨다.
readelf는 멀쩡히 파싱하는데 ld.so는 세그폴트하는 파일이 왜 가능한가? 둘이 같은 ELF를 읽는데?
가르는 것: SHT뷰 vs 로더뷰 분리
암기 답: "관점이 달라서." 깊은 답: readelf는 섹션 헤더(SHT) 기반, ld.so는 섹션 헤더를 아예 안 보고 프로그램 헤더/PT_DYNAMIC만 신뢰. 섹션 헤더를 위조하면 분석기만 속고 로더는 전혀 다른 바이트를 본다.
mutate_elf_v4의 keep 모드에서 repair_pht()가 하는 일은? 이게 없으면 무슨 일이 나고, 왜 그게 문제인가?
가르는 것: constraint-repair의 목적
암기 답: "필드 재계산." 깊은 답: 뮤테이션으로 깨진 교차필드 불변식(예: p_offset/p_filesz)을 복구해 파일이 로드는 되게 유지. 안 하면 로더가 초기 검증에서 즉시 거부 → 깊은 코드경로 도달 실패("너무 invalid하면 빨리 거부됨").
likelihood(-l)를 100%로 올리면 버그를 더 잘 찾을까? critical 필드에서 규칙이 스스로 확률을 낮추는 이유와 엮어 답하라.
가르는 것: too-valid/too-invalid 균형
암기 답: "확률 파라미터." 깊은 답: 100%면 모든 필드가 동시에 깨져 semi-valid를 벗어나 거의 다 거부 → 커버리지 오히려 ↓. critical 필드는 깨지면 하위 전부 무효라, 그 규칙만 확률을 낮춰 나머지가 살아있게 한다.
generators/numbers의 값이 왜 순수 랜덤이 아니라 0xbad0c0de·0x7fffffff·0xffffffff 같은 경계값 위주인가?
가르는 것: 파싱 버그의 본질
암기 답: "특수한 값들." 깊은 답: 파싱 버그는 nElem*size 오버플로, size/entsize=0, off+len wrap 같은 경계에서 터진다. 랜덤은 그 좁은 표적을 거의 못 맞히고, 경계값은 직격한다.
logger가 '어느 규칙이 어느 오프셋을 어떤 확률로 때렸는지' 기록하는 게 왜 퍼저에서 선택이 아니라 필수인가?
가르는 것: 재현성
암기 답: "로그 남김." 깊은 답: 크래시를 찾아도 어떤 뮤테이션이 원인인지 모르면 최소재현·트리아지·패치 전부 불가. 시드+규칙+오프셋+확률 기록이 있어야 크래시를 결정적으로 되살린다.
Melkor 구조를 가져오되 언어를 C→Python으로 바꿨는데도 '구조를 미러링했다'고 말할 근거는? 반대로 Python이라 못 가져온 Melkor 메커니즘 하나를 대라.
가르는 것: 구조 vs 구현 구분
깊은 답: 역할 분리(main/rules/generators/logger)는 언어 무관하게 이식됨. 단 Melkor의 __attribute__((constructor))로 함수포인터 배열을 자동 등록하는 건 C 고유 → Python은 import 시 RULES 리스트/데코레이터로 대체한다.
지금 Lfuzzer가 '의존성 레벨을 통합적으론 미고려'라는 말의 정확한 의미는? repair_pht가 있는데도 왜 '미고려'라 하나?
가르는 것: 국소 수선 vs 통합 엔진
깊은 답: repair_pht는 PHT 한 영역의 국소 불변식만 복구할 뿐. 영역 간 레벨 순서(HDR→PHT→dynamic)나 깊이별 확률 스케줄링이 없음 → 어느 레벨을 얼마나 때릴지 조율하는 상위 정책이 부재. 그래서 "부분적 있음, 통합적 없음".
차등(gold≠bfd) 불일치가 진짜 '로더가 다르게 동작'하는 건지 그냥 '링커가 다른 출력을 냈을 뿐'인지 어떻게 구분하나? 이 구분이 왜 중요한가?
가르는 것: 링크타임 vs 런타임 차등
깊은 답: 두 링커 출력이 다른 건 흔함(정상). 진짜 신호는 "양쪽 다 링크 성공한 뒤 같은 ld.so로 실행했을 때 런타임 거동이 갈리는가". 이 구분을 놓치면 링커 구현차이를 로더 버그로 오인한다. (당신이 실제로 교정한 그 지점.)

추천 빌드순서: V5 → V1 → V2 → V3 → V4(글루). V5 먼저(비용~0, 지표를 결정론화해 이후 이득 측정 가능) → V1(최대 발견승수) → V2(V1 위에 구조입력) → V3(병렬 차등트랙) → V4는 back-edge 데몬만. "이번 주 하나만 = V5, baseline 위 하나만 = V1." 어떤 단일 변이도 대조군 조합을 못 이김 → 스택이 곧 대조군 재조립.
작업1(MCP 트리아지) 답. MCP/LLM은 자문만, 판정 절대 안 함. 권위=CASR(유니크·심각도). 규칙: 모든 LLM 주장은 도구결과 인용 필수, 없으면 폐기. 지표 숫자는 LLM 안 읽음(결정론). LLM 값어치 = 스택해시가 잘못 병합한 버킷 분할(진짜 유니크 회수) + 논문용 자연어 재현.
